# VTB AgentPay — MVP

Банковский слой агентной коммерции. Клиент описывает покупку обычным языком, ИИ-агент собирает и сравнивает предложения продавцов, детерминированный код проверяет условия и платёжные правила, а платёж проходит только после явного подтверждения человеком.

**ИИ готовит покупку, но не распоряжается деньгами.**

> Конкурсный проект команды SYNQ (Академия Финтеха 2026, кейс ВТБ). Не является продуктом Банка ВТБ (ПАО). Все платежи — sandbox, реальных списаний нет; каталоги продавцов тестовые.

**Соответствие требованиям кейса:** работающий сквозной сценарий (не только слайды) · генеративный ИИ на on-prem модели, есть подключение российских моделей · работа в закрытом контуре без доступа к открытой сети · open-source-компоненты · метрики качества и безопасности, воспроизводимые одной командой · стенд в Docker Compose и CI.

## Сквозной сценарий

1. **Поручение:** «Найди SSD Samsung 2 ТБ с гарантией и доставкой до пятницы».
2. **Агент:** извлекает ограничения, опрашивает три тестовых каталога (у каждого своя схема данных), нормализует предложения.
3. **Проверка кодом:** бренд, категория, модель, объём, бюджет с учётом доставки, срок, гарантия, наличие, целостность карточки (prompt injection, чужие реквизиты, в том числе замаскированные). Карточка с недопустимыми значениями (цена ≤ 0, отрицательный срок) отбрасывается.
4. **Заказ:** сумма в копейках берётся из повторно запрошенной карточки продавца, реквизиты получателя — из реестра банка.
5. **Policy Engine:** 13 правил до подтверждения и повторно после него, прямо перед списанием. Условия поручения перепроверяются по актуальной карточке; по одному поручению оплачивается только одна покупка. Лимит на одну покупку понижается сразу, а повышается только кодом с устройства.
6. **Подтверждение:** одноразовый код приходит отдельным каналом (в sandbox — имитация push на устройство), а не в ответе API. Код привязан к HMAC заказа, не больше 3 неверных попыток на заказ и 3 запросов кода.
7. **Платёж в sandbox и журнал:** журнал ведётся только на добавление, записи связаны цепочкой HMAC с ключом сервера.

## Зоны доверия

```
 Пользователь ──► Web UI (React)
                     │
   ┌─────────────────┼──────────────── НЕДОВЕРЕННАЯ ЗОНА ───────────┐
   │  Разбор поручения: LLM on-prem (Ollama) │ правила (запасной)    │
   │  Адаптеры каталогов продавцов (цены и описания — любые)         │
   └─────────────────┬───────────────────────────────────────────────┘
          только Constraints / Offer после проверки схемы (Pydantic)
   ┌─────────────────▼──────────────── ДОВЕРЕННАЯ ЗОНА ─────────────┐
   │  Verifier → Сервис заказов → Policy Engine → Подтверждение     │
   │  → Платёжный sandbox → Журнал (append-only, цепочка HMAC)      │
   │  Хранилище: PostgreSQL или SQLite, одна транзакция на операцию │
   └─────────────────────────────────────────────────────────────────┘
          код подтверждения ──► устройство клиента (отдельный канал)
```

Модель видит только текст поручения. Она не читает карточки товаров, у неё нет инструментов заказа и оплаты, а объяснение для пользователя собирается шаблоном из проверенных полей.

### Защита платёжного контура

- **Клиенты изолированы.** Поручения, заказы, платежи, лимиты и записи журнала привязаны к сессии (cookie HttpOnly, SameSite=Strict). Чужой объект для API неотличим от несуществующего.
- **Подтверждение — действие человека.** Код не возвращается тому, кто запрашивает оплату. Он приходит на устройство клиента, хранится только как HMAC, повторный запрос кода не обнуляет счётчик попыток. Отклонённый заказ не «оживает».
- **Атомарность.** Проверки Policy Engine, счётчик попыток и запись платежа выполняются в одной транзакции под блокировкой записи (SQLite — `BEGIN IMMEDIATE`, PostgreSQL — advisory lock). Параллельные запросы не обходят ни лимит попыток, ни дневной лимит. `UNIQUE` в схеме не даёт записать второй платёж по заказу или поручению.
- **Деньги** — целые копейки, дневной лимит считается по банковскому дню (`AGENTPAY_TZ`, по умолчанию Europe/Moscow).
- **Целостность.** Хеш заказа и цепочка журнала — HMAC-SHA256 с ключом вне базы: с доступом только к базе запись не подделать и цепочку не пересчитать. Журнал защищён триггерами от UPDATE и DELETE (в PostgreSQL — и от TRUNCATE).
- **Журнал только на добавление — и на уровне базы.** Схему создаёт отдельный `python -m app.migrate` под владельцем таблиц, а приложение работает под ролью `agentpay_app`: в журнал только `SELECT` и `INSERT`, снять триггер или переписать запись нельзя даже из процесса приложения.
- **Нагрузка и ввод.** Ограничение частоты поручений (на сессию и адрес) и новых сессий; тело запроса к API не больше 64 КБ; идентификаторы проверяются на входе.
- **Веб.** CSP только для своих ресурсов, `frame-ancestors 'none'` (окно подтверждения нельзя встроить в чужую страницу), раздача фронтенда без выхода за пределы `dist`, клиенту не уходят внутренние адреса контура, схема API скрыта без `AGENTPAY_API_DOCS=1`.

Подробно, с воспроизведением каждого найденного дефекта: [docs/REVIEW.md](docs/REVIEW.md).

## Запуск

### Docker Compose: backend, frontend, PostgreSQL, Ollama

```bash
cp .env.example .env    # заполнить POSTGRES_PASSWORD, POSTGRES_APP_PASSWORD и AGENTPAY_SECRET_KEY (команды генерации — в файле)
make up                 # http://localhost:8080
docker compose exec ollama ollama pull qwen2.5:3b   # модель; в закрытом контуре — заранее загруженный том
```

Без модели backend разбирает поручения правилами и переключается на модель, как только она становится доступна. Перед backend разово запускается `migrate`: схема и роль приложения создаются под владельцем таблиц. Секретов в репозитории нет: без `.env` compose не стартует.

### Локально

Нужны Python 3.12 (через [uv](https://docs.astral.sh/uv/)) и Node.js 18+.

```bash
make install   # зависимости строго по зафиксированным версиям и хешам
make run       # сборка фронтенда и сервер на http://localhost:8000 (SQLite в backend/data)
```

Режим разработки: `make backend` (API на :8000) и `make frontend` (Vite на :5173 с прокси на API).

### Языковая модель: on-prem или российская

Без модели поручения разбираются детерминированными правилами. Ответ любой модели проходит проверку схемы и сверку с текстом поручения ([`grounding.py`](backend/app/agent/grounding.py)).

**On-prem через Ollama** (по умолчанию, проверено):

```bash
ollama pull qwen2.5:3b        # или российская T-lite / другая open-weights модель
```

**Любой OpenAI-совместимый API**: vLLM в контуре банка, MLX-сервер, DeepSeek, YandexGPT, GigaChat через совместимый прокси. Адрес, модель и ключ — в переменных окружения или в `.env` (его читают `make backend`, `make run`, `make eval`, `make eval-llm` и Docker Compose; в git файл не попадает).

```bash
AGENTPAY_LLM=openai AGENTPAY_LLM_BASE_URL=http://vllm.internal:8000/v1 AGENTPAY_LLM_MODEL=<модель> make backend
```

**Qwen3-8B на Mac (MLX, 4 бита).** OpenAI-совместимый сервер `mlx_lm.server` или LM Studio:

```bash
mlx_lm.server --model mlx-community/Qwen3-8B-4bit --port 8081
AGENTPAY_LLM=openai AGENTPAY_LLM_BASE_URL=http://127.0.0.1:8081/v1 AGENTPAY_LLM_MODEL=mlx-community/Qwen3-8B-4bit make eval-llm
```

У Qwen3 по умолчанию включён режим рассуждений: ответ начинается с `<think>…</think>`, а рассуждение здесь не нужно — задача только извлечь поля. Для моделей qwen3 оно выключается (`chat_template_kwargs.enable_thinking=false` и `/no_think` в системном промпте; `AGENTPAY_LLM_THINKING=on|off` — вручную). Если сервер всё же вернул рассуждение, обернул JSON в ```` ```json ```` или не поддерживает `response_format`, ответ всё равно разбирается: рассуждение и текст вокруг JSON вырезаются, а запрос повторяется без `response_format` ([`llm.py`](backend/app/agent/llm.py), тесты — [`test_llm.py`](backend/tests/test_llm.py)).

**DeepSeek** (OpenAI-совместимый API):

```bash
AGENTPAY_LLM=openai AGENTPAY_LLM_BASE_URL=https://api.deepseek.com AGENTPAY_LLM_MODEL=deepseek-chat make eval-llm
# ключ — только в AGENTPAY_LLM_API_KEY через .env или секреты окружения
```

> **DeepSeek — внешний API.** Текст поручения клиента («SSD Samsung 2 ТБ до 16 тысяч к пятнице») уходит на серверы DeepSeek, то есть за пределы контура банка. Это требует согласования с ИБ банка и оценки по 152-ФЗ, если в поручении могут оказаться персональные данные. Поэтому по умолчанию остаётся модель в контуре (Ollama, vLLM, MLX), а DeepSeek — опция для сравнения качества. Карточки товаров, суммы, реквизиты и коды подтверждения модель не видит ни в одном режиме.

С YandexGPT и GigaChat не проверялось: нужны ключи доступа. `make eval-llm` сначала проверяет, что модель отвечает, и падает, если нет: цифры разбора правилами не выдаются за цифры модели. Отчёт называется по модели (`backend/eval/report_llm_grounding_<модель>.md`) и показывает, сколько поручений модель разобрала сама.

### Закрытый контур

Фронтенд не обращается к внешним ресурсам: шрифт Onest (OFL) лежит в сборке файлами woff2, иконки — свой SVG-набор, CDN нет, это закреплено CSP. Бэкенд обращается только к модели по адресу из настроек, к каталогам продавцов и к своей БД. В MVP каталоги — локальные файлы, клиентские данные банка не используются. Swagger UI, которому нужен CDN, по умолчанию выключен.

## Сценарии атак в интерфейсе

Вкладка **Sandbox**: рост цены у продавца, товар закончился, подмена реквизитов в заказе, истёкший код подтверждения, изменение лимита на одну покупку (повышение — только кодом с устройства). Сценарий действует только на клиента, который его запустил. Карточка с prompt injection уже лежит в каталоге «Комплект-Про» («СУПЕРЦЕНА»). Код подтверждения показывается в окне оплаты как push-уведомление: интерфейс берёт его из отдельного канала `/api/sandbox/device`, а не из ответа на запрос оплаты.

Остальные атаки из прогона метрик (подбор кода, параллельные запросы, чужой заказ, изменение карточки после проверки) воспроизводятся тестами и `make eval`.

## Что не входит в MVP

Реальные карты и списания, покупки на произвольных сайтах, доступ агента к банковскому счёту, интеграция с ВТБ без согласования, вход через ВТБ Онлайн (в MVP клиент — анонимная сессия). Список доработок для промышленного контура — в [docs/REVIEW.md](docs/REVIEW.md#что-осталось).
